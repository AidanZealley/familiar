# Familiar daemon

The installable Familiar: core and its Node building blocks, plus opinions. It adds the web search and fetch tools, the owner's own plugins from the data directory, ChatGPT sign-in, Web Push, CLI setup and services. It serves core's HTTP API and the built web UI. [examples/node-server](../../examples/node-server/) is built from the same pieces without those opinions.

User guides, including commands, settings and notifications, are under [Use Familiar](https://aidanzealley.github.io/familiar/use/install/) (publishes once GitHub Pages deployment is enabled).

## Installed assistant

Run the [installer](../../README.md#install), then open the URL it prints. Run `familiar --help` for commands.

The daemon listens on `127.0.0.1:4317` and authenticates every request as its owner, with the stable author ID `owner`. Setup publishes a private HTTPS URL when Tailscale is available. There is no separate app login: anyone with access can use the conversation, change credentials and install MCP tools, and local MCP commands run as the daemon's user. Keep the endpoint private.

The owner's plugins are `.ts` and `.js` files in `plugins/` in the data directory, loaded at start by [src/plugins.ts](src/plugins.ts). A file that fails to load is skipped and logged. [Extend your Familiar](https://aidanzealley.github.io/familiar/use/extend/) is the guide.

Settings live in `settings.json` in the data directory (`~/.local/share/familiar` on Linux, `~/Library/Application Support/Familiar` on macOS, `%LOCALAPPDATA%\Familiar` on Windows). `FAMILIAR_NAME`, `FAMILIAR_OWNER`, `FAMILIAR_PORT`, `FAMILIAR_MODEL`, `FAMILIAR_HOST` and `FAMILIAR_DATA_DIR` override them. Model choices live in [src/config.ts](src/config.ts).

## Development

From the repository root:

```sh
pnpm install
pnpm dev
```

This starts the scripted daemon on port 4318 and the UI on 5174 with disposable in-memory data. It opens on Rowan's household, a few days in: four Familiars, their DMs and rooms, memory, schedules and connections, with Spool still busy watching a print. The household is written as data in [src/demo/household/story.ts](src/demo/household/story.ts), each message with the replies it gets; add to it there. Anything the story doesn't script falls back to the scenarios: try `tool`, `memory`, `remind`, `key`, `mcp`, `slow`, `compact` or `error` in Juniper's DM, which has the demo plugin. Only the model and external services are simulated. Add scenarios under `src/demo/scenarios/` and register them in `src/demo/model.ts`.

`pnpm start` serves the real assistant; `pnpm sign-in` changes its saved provider login. In this package, `pnpm dev:live` starts a real daemon too. Use these only when you intend to work with that installation. Never run a second daemon over its storage. Leave the running service, port 4317 and its data untouched during ordinary development.

`pnpm eval:recall` and `pnpm eval:unfiled` check memory retrieval against a scripted year of conversation, in [src/memory-eval](src/memory-eval/), without a model. Results are saved under `eval/results`.

`pnpm eval:core` grades what memory upkeep keeps and where it puts it. It replays two months of a household's messages (64 messages on 15 active days, 39 labelled items, at least 7 per label), labelled with where each thing belongs, through a real workspace. Replies are scripted and free; only upkeep calls a model, Claude Haiku 5.5 at low thinking (`--model` picks another Anthropic model). It needs an eval-only Anthropic API key in `ANTHROPIC_API_KEY` or `~/.local/share/familiar-eval/anthropic-api-key`, never your sign-in. `--replays N` (default 3) replays the scenario N times, because upkeep's model writes different memory each time and one replay is one draw. Each replay measured 410k–580k tokens (under $0.15 on Haiku) and 4–5 minutes, so the default three cost about 1.5M tokens. Each replay stops once it passes `--max-tokens` (default 1,500,000), and after its first 3 active days it prints tokens, time and a projection and stops if the projection is over the cap (it underestimates, since later days cost more as memory grows; expect about 2.5 times). `--probe` runs only those 3 days of the first unsaved replay. Each replay's final memory is saved in `eval/fixtures/core-<hash>-<replay>.json`, keyed by upkeep's prompts and tools, the scenario and the model, and numbered. Until one of those changes, a rerun only grades the fixtures, re-running the current core ranking first, so ranking changes are measured free. Every replay is graded separately, and the printout gives each measure's mean with the range across replays, then lists items that missed their label in any replay.

Core is graded twice. The scenario fills only about a sixth of the real budget, so at that budget ranking never chooses anything. The second grade, under `pressure`, cuts the budget to a tenth (`PRESSURE_BUDGET`), where the facts that qualify for core no longer fit and ranking has to decide. `fadesRefreshed` reports `fades` items with a fact recalled after the last message that names them. Recall counts a message that merely shares a word with a fact as use, so a fade can look used without anyone mentioning it. That is a known problem for re-rating, and the grade shows it rather than hiding it.

`pnpm eval:use` grades how the reply model uses memory. Thirty proactive probes, four restraint and four attribution, in [use-probes.ts](src/memory-eval/use-probes.ts), each run in a fresh workspace whose chat is Claude Haiku 5.5 at low thinking. Each probe's facts are planted and placed by `rebalanceCore`, and upkeep never runs, so it measures the reply alone. Proactive probes (memory should change the reply) run three ways: with their facts pinned into core, with them rated just below core's threshold so only recall can bring them up, and with memory empty. Core against empty is the memory gain. The rescue rate is how many probes that pass from core still pass from outside it; it prints directly under the in-core rate, so a drop in either shows. The result also records whether recall's word search matched the request (`recalled`) and whether the model searched memory itself (`asked`), so a miss can be told apart from a reply that ignored what it was given. Each probe says beside it the principle it tests and whether its request shares a word with its fact; half share none, which is where word search is blind. Required strings are names or specifics a reply can only say if it used the fact, never a hedge. `--repeat N` (default 3) runs each proactive probe N times per placement and reports every rate as the mean with the range across repeats, followed by a per-probe table of passes in each placement, to find a probe that is broken rather than telling. Restraint probes (unrelated requests must not mention memory) and attribution probes (in a room, one person's facts must not be applied to another) run once, with their facts as seeded. Grading is by case-insensitive strings kept beside each probe. It needs the same key as `eval:core`, takes `--model` and `--max-tokens` (default 1,500,000, or 2,000,000 when repeating), and after one probe of each kind prints tokens, time and a projection, stopping if the projection is over the cap. `--probe` runs only those five runs (about 15–20k tokens). One repeat is 98 runs, about 360k tokens and 5 minutes, so the default three are about 1.1M tokens and 15 minutes. `--from-fixture eval/fixtures/core-<hash>-<replay>.json` seeds every probe from that replay's current facts instead, runs proactive probes as placed and empty, and runs only the probes whose tested strings those facts contain, to test writing and using together. Results are saved under `eval/results` as `use-*` (`use-fixture-*` for fixture mode).

Reading spread: each measure is shown as `mean (min–max)` across repeats or replays. A move between runs that is smaller than that range is not evidence of a change; only a move past the range is. Three draws only sample the range, so treat a move just past it as a hint and repeat it. A measure at 0% or 100% in every run, such as in-core and none, has no resolution; those two are the ceiling and floor controls, not targets.

`pnpm bundle` creates the installable tarball; `pnpm test:release` verifies it using temporary storage. Both run from the repository root. The [release workflow](../../.github/workflows/release.yml) publishes tagged releases.

Start reading at `src/cli.ts`, the entry, then `src/daemon.ts`, which assembles the host, `src/serve.ts`, `src/config.ts` and `src/web/`, the web plugin. Platform setup is under `src/cli/`. Portable assistant capabilities belong in [core](../../packages/core/README.md), not this host.
